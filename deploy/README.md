# Постоянный сервер для личного приложения

Целевая схема: интерфейс на существующем Vercel → HTTPS API на VPS → SQLite на постоянном диске. Монитор запускается внутри API-процесса даже при закрытом Mini App. Только один экземпляр процесса: SQLite и подавление повторов не рассчитаны на несколько реплик.

## Требования и текущие ограничения

Для начальной нагрузки выбираем Linux VPS с 2 vCPU, 2–4 ГБ RAM и 25–50 ГБ диска. Это предварительная оценка, а не проверенная производительность всех площадок. Нужны Docker Engine с Compose и DNS-имя API, указывающее на IP сервера. Сертификат выпускает Caddy; DNS должен быть настроен, порты 80/443 доступны. Порт 4173 наружу не публикуется. SSH-доступ и резервное копирование настраиваются отдельно.

Монитор проверяет **локальный нормализованный снимок** раз в две секунды. Для каждого адаптера частота запросов должна соответствовать лимитам площадки; предпочтительны документированные потоки событий, если они доступны. Обновления источника старше десяти секунд отклоняются. Фактическая задержка состоит из задержки площадки, доставки события/поллинга адаптера, цикла сопоставления и обработки запроса покупки. Интервал 2 секунды не гарантирует сделку за 2 секунды.

Адаптеров, действующих торговых сессий и покупок ещё нет. Уведомления отправляются последовательно, сетевые задержки могут увеличить цикл. До интеграции торговли путь покупки следует отделить от очереди уведомлений и измерить задержку на реальных API. Не включать покупки без дневного бюджета, лимита на сделку с комиссиями, блокировки повторной покупки, проверки актуальной цены и обработки неопределённого результата сделки. Сейчас сервер всегда отклоняет включение автопокупки.

## Развёртывание подготовленного проекта

1. На компьютере выполните `pnpm install --frozen-lockfile`, `pnpm test`, `pnpm build`. Dockerfile использует готовую папку `dist`, чтобы не собирать клиент на маленьком VPS. Перенесите проект без `node_modules`, `.git`, токенов и тестовых баз на сервер.
2. На сервере из корня проекта скопируйте `deploy/.env.example` в `.env`, задайте настоящий `APP_DOMAIN`, собственные `BOT_TOKEN` и `OWNER_ID`. Не отправляйте токен в чат или в GitHub. Права `.env`: `chmod 600 .env`.
3. Оставьте `APP_ORIGIN` равным production URL клиента на Vercel. Если размещаете также клиент на VPS, задайте `https://ваш-домен` и поменяйте URL Mini App в BotFather.
4. Создайте каталог источника: `mkdir -p data/feeds`. Будущий адаптер должен атомарно заменять `data/feeds/market.json` в формате основного README. Источник пока отсутствует; пустой или старый файл не используется.
5. Выполните `docker compose build`, затем `docker compose up -d`. Проверьте `docker compose ps` и `curl --fail https://ваш-домен/healthz`. У API без Telegram-авторизации ожидается 401. Healthcheck показывает работоспособность HTTP, а не готовность торговли. Docker restart policy перезапускает завершившийся процесс; статус unhealthy сам по себе не вызывает перезапуска.
6. Для сохранения Vercel: замените `api.example.com` в `deploy/vercel.proxy.example.json`, объедините rewrites с существующим `vercel.json` в корне. Не затирайте уже существующие правила. Опубликуйте клиент только после проверки API и авторизации владельца. Не публикуйте `LOCAL_PREVIEW=1`.
7. Проверьте в Telegram доступ владельца и отказ другому аккаунту, создание/перезапуск/сохранение подписки, обновление живого источника и доставку уведомлений. Финансовые операции требуют отдельных end-to-end проверок.

Не выполняйте `docker compose down -v`: эта команда удаляет постоянные тома, включая SQLite. Для резервной копии сначала остановите app, скопируйте том `app_data` защищённым способом и затем запустите app. Одного архива исходников недостаточно для восстановления подписок.
